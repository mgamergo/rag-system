RAG system · complete architecture study guide

From source text to grounded answer

This repository has two implementations of the same RAG idea. The TypeScript CLI provides retrieval and evaluation experiments. The Field Notes web app uses Convex and OpenRouter for storage, vector search, and model calls. This guide explains both, their shared concepts, and where they differ.

The core idea: ingestion turns a document into overlapping chunks and embedding vectors. A question becomes one vector, retrieval selects related chunks, and a chat model receives those chunks as evidence for an answer. Everything else improves, stores, measures, or presents that loop.

TypeScript request flow

Ingest once

npm run ingest --
  → find .md and .txt files
  → parse UTF-8 text
  → create chunks with offsets
  → optional Anthropic context
  → embed chunks
  → write linked JSONL artifacts

Each chunk has a UUID, source path, chunk index, original text, offsets, and optional context. Embeddings refer back to chunks through the same UUID.

Answer many questions

npm run ask --
  → load artifacts
  → semantic, BM25, TF-IDF, or hybrid retrieval
  → optional reranking
  → grounded provider request
  → answer and source list

runRag owns the orchestration. It returns an answer plus RetrievedChunk objects, which preserve score and evidence metadata.

How a document becomes searchable

  1. The browser reads a file.

    The UI accepts UTF-8 .md and .txt files and calls api.rag.ingest.

  2. The action normalizes and chunks text.

    convex/rag.ts removes a byte-order mark, normalizes newlines, then makes 1,800-character chunks with 200-character overlap.

  3. OpenRouter embeds batches.

    Each batch holds up to 32 chunk texts. Every response must contain 2,048 finite values per vector.

  4. Convex stores indexing chunks.

    Each chunk saves text, offsets, vector, model name, document ID, and indexing status.

  5. Convex marks the document ready.

    After every batch succeeds, the document and its chunks become ready. Incomplete chunks never enter search.

Why chunks overlap

A chunk boundary can split a claim. The repeated 200 characters make it less likely that retrieval omits the beginning or end of a thought.

chunk 1: [0 .................... 1800)
chunk 2:              [1600 .................... 3400)
                         ^ 200 characters repeated

Offsets are character positions in normalized text. They make evidence inspectable later.

How a question becomes an answer

  1. The browser calls api.rag.ask.

    It sends a question and asks for six source chunks. The UI disables the button while the action runs.

  2. The action embeds the question.

    The same embedding model creates a 2,048-dimension query vector. Query and document vectors must share model and dimensions.

  3. Convex finds nearest vectors.

    ctx.vectorSearch searches chunks.by_embedding and includes only chunks where status = ready.

  4. The action loads chunk text.

    Vector search returns IDs and scores. The action loads full chunk records in retrieved order.

  5. Gemma answers from evidence.

    Gemma receives a system instruction, the question, and labelled source texts. The prompt asks for citations such as [1].

  6. A trace is saved.

    The app stores the answer, source IDs, models, token counts when available, and stage timings.

Gemma sees only retrieval results

It does not read the whole library. Retrieval quality therefore limits answer quality.

Current web behavior: semantic vector retrieval only. It does not yet use BM25, hybrid rank fusion, or reranking from the TypeScript pipeline.

The vector index

chunks.by_embedding indexes each chunk’s embedding. It accepts 2,048 dimensions because that is the selected embedding model’s output size.

.vectorIndex("by_embedding", {
  vectorField: "embedding",
  dimensions: 2048,
  filterFields: ["documentId", "status"],
})

Why status exists twice

An indexing run can fail after some chunks are stored. Chunks stay visible for diagnosis, but their indexing status keeps them out of search.

That protects questions from incomplete documents.

Keep this security boundary

Do not put OPENROUTER_API_KEY in a NEXT_PUBLIC_ variable. Every public Next.js variable is visible to the browser. Convex reads the key from its server environment.

Changing models changes different things

Changing the generation model is safe because it does not change stored data. Changing the embedding model changes the vector space. Reindex all documents after an embedding model or dimension change.

Where evaluation will connect later

The TypeScript evaluator already measures retrieval against labelled JSONL questions. The web traces table records what the deployed app retrieved and answered. Neither one alone tells you whether an answer is fully correct.

What exists today

npm run evaluate -- accepts questions with relevant chunk IDs or source paths. It runs one or more retrieval methods and calculates recall at k, failure rate, hit rate, MRR, and latency.

The web trace records selected chunk IDs, answer text, model names, token usage when returned, and retrieval, generation, and total latency.

What you will add later

Build one stable human-written dataset with question, expected answer, answerable flag, source passage, and offsets. Map those passages to current chunk IDs after each reindex. Then compare gold evidence with retrieval traces and grade answer grounding separately.

A 10-day study path

Read the system in request order

End each day with one observation in the app or Convex dashboard.

  1. Run the app and upload one short note.

    Read features/rag/RagWorkspace.tsx. Watch the library become ready.

  2. Follow ingest line by line.

    Find normalized text, chunks, the OpenRouter batch, and the first database mutation.

  3. Inspect Convex data.

    Verify one document’s chunk indexes and offsets overlap as expected.

  4. Understand the embedding contract.

    Explain why queries and documents share the same 2,048-dimension model.

  5. Ask one direct question.

    Expand evidence in the UI and compare an answer claim to the exact chunk text.

  6. Follow ask line by line.

    Start at query embedding, then vector search, source loading, prompt construction, and trace write.

  7. Inspect a trace row.

    Find its question, source IDs, timings, model names, and token counts in Convex.

  8. Create a retrieval failure.

    Ask for something absent from the corpus. See that nearest-neighbor search still returns chunks and why the prompt asks for abstention.

  9. Compare web and TypeScript.

    Read src/retrieval/search.ts and list what the TypeScript pipeline has that the web path lacks.

  10. Write five labels by hand.

    For each question, record the supporting paper passage and offsets. Do not tune retrieval yet.

Glossary

Embedding

A fixed-length list of numbers that represents text. Nearby embeddings are intended to represent related text.

Vector search

A nearest-neighbor lookup. It finds stored vectors closest to the query vector, then returns IDs and scores.

Chunk

A bounded document excerpt. Chunks are both retrieval units and evidence sent to the answer model.

Action

A Convex server function. Actions can call external services with fetch and invoke queries or mutations.

Trace

A stored record of one answer request. Here it includes timings, tokens, models, selected sources, the question, and answer.

Grounding

Constraining an answer to supplied evidence. It improves inspectability but does not guarantee that the model follows the instruction.
